A 35-billion-parameter AI assistant, running on your iPhone

Millie runs entirely on your phone in roughly 4 GB of memory—delivering stronger benchmark performance, faster generation, and lower memory use than a leading 27-billion-parameter phone model.

We built Millie because we want capable AI to run on hardware people already own. Our first release brought local coding to Macs and Linux PCs. Now we’re bringing Millie to the iPhone.

We trained the compressed model, built the memory-saving runtime and kernels, and brought them together in an iPhone app.

You can talk through an idea, work on a message, or ask about a photo. Your conversations stay on your device, with no account required. Once the model is downloaded, it works offline.

Model quality

We evaluated how well Millie answers across knowledge, reasoning, coding, and instruction-following tasks. “Unrestricted” runs the compressed model normally with a 16-bit KV cache. The phone memory configuration biases the model toward selecting resident experts—those already in RAM—and loads others as needed. It also uses an 8-bit Q8 KV cache to reduce the memory needed for conversation context.

Capability after compression and memory savings

Despite its extreme compression, Millie retains much of the original model’s capability. In phone memory mode, it scores 91.68% on MMLU Redux versus 93.94% for Qwen 3.6, 91.46% versus 93.29% on HumanEval+, and 66.40% versus 66.93% on MuSR. It also outperforms 1-bit Bonsai across every benchmark tested.

Moving to the memory-restricted configuration did not appear to affect performance on average. Scores are slightly noisy because each evaluation used a single sampled run, but these results show no obvious overall difference.

The evaluations simulate the phone’s expert-routing configuration and Q8 KV cache; they were not run on the phone itself.

Speed in use

There are two parts to responsiveness. Prefill is the time spent reading a prompt or conversation before generating an answer. Decode is the rate at which the answer is generated. Both matter: a model that writes quickly can still leave you waiting if it takes a long time to read what you sent.

Using the current shipping model on an iPhone 17 Pro, Millie generated real answers at 17.72 tokens per second. For context, PrismML reports 11.0 tokens per second for 1-bit Bonsai 27B on an iPhone 17 Pro Max. Our 17.72 tokens/s result is about 60% higher, despite a larger workload: a 729-token starting context and 238 generated tokens, versus Bonsai’s depth-zero, 128-token test.

For 512-token prefill, Millie took 3.80 seconds, or 134.6 tokens per second, versus Bonsai's published 111 tokens per second. Millie processed the input in 128-token microbatches.

The harness uses the shipping inference framework, 64 resident experts per layer, a +1 routing bias, a Q8 attention cache, and a 20,480-token context allocation. Getting the whole thing onto a phone

A small model file is only part of the problem. The phone also needs memory for the conversation, intermediate computations, image processing, and the app itself. And an app cannot use all of the RAM listed in the phone's specifications.

Millie's flagship is a mixture-of-experts model: it contains many groups of weights, called experts, and selects a small number for each token it processes. It has 35 billion parameters in total, with roughly 3 billion active per token. That gives us a way to reduce both computation and the amount of model data that needs to stay in memory.

We combine a trained, highly compressed model with an open-source runtime that keeps a subset of its experts in RAM, biases the model toward selecting those resident experts, and loads others from storage as needed. The low-memory configuration also uses a Q8 KV cache. Its expert weights use a ternary representation: each weight is zero, positive, or negative, with shared scaling factors. Our mask-and-sign encoding stores these weights in 1.5 bits each before scaling overhead, with at least half constrained to zero. The model, the kernels that perform its calculations, and the way we manage memory all matter. Compressing the weights alone would not give us the same result.

The resulting system runs in roughly 4 GB of memory, including the vision encoder and conversation state. Memory use varies with context and workload. The flagship reliably supports iPhone 15 Pro and Pro Max, and iPhone 16 and newer.

In a separate text-only memory test on the physical iPhone 17 Pro, Millie peaked at 3.63 GB while processing a 20,000-token prompt and generating another 128 tokens. This run used a Q8 KV cache. It completed without memory warnings or elevated thermal readings.

For comparison, PrismML publishes the following text-only peak memory figures for 1-bit Bonsai 27B:

In internal tests, we have even run the flagship on an iPhone 14 Pro Max with only 6 GB of RAM, including at long contexts. But memory pressure can cause warnings or crashes on that device, so we chose not to make the flagship available on 6 GB phones. The smaller Millie Flash model is available on supported older phones.

Other approaches to compression and memory savings

PrismML also offers the original ternary Bonsai 27B and ternary Bonsai 2 27B, announced on September 17. These larger dense models are very unlikely to run well within the memory budgets of the iPhones we target. The original ternary build occupies about 7.2 GB; Bonsai 2's compact packing uses 5.95 GB for language weights alone, while its alternative packing uses 7.21 GB. PrismML publishes no phone throughput figures for these ternary releases. Original release, Bonsai 2 model card.

Our iPhone 17 Pro exposes roughly 6 GB to the app, and many of the phones we target have only 8 GB of physical RAM in total. A dense model whose weights alone consume nearly the entire app budget leaves insufficient room for its conversation cache, intermediate computations, and the app. Offloading dense layers to storage would require rereading those weights for every generated token. That is much more expensive than loading the small subset of experts selected by a sparse model. This is why we treat the 1-bit Bonsai release as the practical phone comparison, and do not consider the larger ternary or conventional 2-bit dense 27B builds suitable for our target phones.

Edge0 streams experts from storage. We compared its released macOS runtime with Millie on the same 24 GiB M5 Mac, reserving 16 GiB to leave roughly 8 GiB for the models, macOS, and other apps.

Real-answer decode under 16 GiB memory pressure Edge0 35B Millie
Explanation of sky colors 2.25 tokens/s 29.85 tokens/s
Python interval-merging function 2.10 tokens/s 29.89 tokens/s

Millie generated answers 13–14 times faster in these two tests. Each task used one run per model with the same prompt, non-thinking template, sampling settings, and 512-token limit. Millie used 64 resident experts per layer and Q8 KV. Its coding answer hit the output limit; the other answers finished naturally.

In a separate inspection, Edge0 reported about 3 GiB of MLX allocations while sampled total process memory (RSS) peaked at 9.9 GiB—its allocator figure alone did not capture the full memory footprint.

Using Millie

The app offers two models. The flagship Millie is for more demanding questions and can understand photos. Millie Flash is smaller and intended for faster replies. You can adjust the flagship's reasoning effort and personalize how Millie responds.

The flagship download is about 8.6 GB, including its vision component. That is larger than its runtime memory footprint because the full model is stored on the phone while only part of the expert weights stays in memory at once. Flash's download is about 2 GB.

After that initial download, you can use Millie without an internet connection. It is useful for conversations you want to keep on your own device, and in places where a cloud assistant is unavailable.
